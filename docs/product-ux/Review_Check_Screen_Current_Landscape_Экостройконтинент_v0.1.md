## Зачем документ

Этот документ нужен как входная точка перед любым новым эпиком вокруг `/admin/review`, согласования, диффов, журнала и повторной отправки карточек на проверку.

Цель: использовать уже существующий ландшафт, а не строить параллельную очередь, второй журнал или отдельный review-flow.

## Что сейчас есть

- `/admin/review` - основной экран проверки для материалов, по которым еще нужно решение или возврат.
- `/admin/review/[revisionId]` оставлен как совместимый маршрут и редиректит на `/admin/review?selected=<revisionId>`.
- Верх экрана компактный: без большой повторяющейся шапки, без блока `Как устроена очередь`, без второго ряда статусных чипов.
- Фильтры остались одним рабочим блоком: поиск, статус, тип, применить, сбросить, счетчик найденных материалов.
- Быстрый фильтр `Доработки SEO` под основными фильтрами - это короткий путь к статусу `returned`. Он сохраняет текущий поиск и тип, показывает счетчик возвращенных материалов и не создает отдельную очередь.
- Карточки показывают только понятный сигнал для согласователя: тип, статус, название, краткое содержание, видимые факты, фото/превью, маркер `Обновлено` при новой версии.
- Модалка проверки показывает пакет решения: превью, понятные изменения, краткое содержание, статус и действия владельца.
- Дифф показывает только то, что изменилось в контенте. Он не принимает решение, не предлагает исправления и не заменяет согласователя.
- Журнал показывает последние действия за 30 дней: отправка, одобрение, возврат, отклонение, замена заявки новой версией, повторная отправка без изменений.

## Словарь статусов

Сырой `state=review` нельзя показывать пользователю как универсальное `На проверке`: это техническая полоса процесса, а не всегда задача собственника.

- `ownerReviewRequired=true` + `ownerApprovalStatus=pending` - `Ждёт решения собственника`. Только этот статус попадает в owner-facing фильтр `Ждут решения собственника`.
- `state=review` + `ownerApprovalStatus=approved` - `К публикации`. Это уже согласованная версия; SEO или другой пользователь с правом публикации завершает работу из карточки материала.
- `state=draft` + `ownerApprovalStatus=rejected` - `Доработки SEO`. Материал возвращён с замечанием и ещё не отправлен повторно.
- `state=published` и live-проекция - `Опубликовано`. Согласование и публикация остаются разными действиями.

Медиатека использует те же термины: быстрый фильтр `Ждут решения` показывает только pending owner approval, а `К публикации` показывает согласованные, но ещё не опубликованные ревизии.

## Повторная отправка

Механика повторной отправки построена на fingerprint содержимого карточки.

- Если SEO-специалист повторно отправляет ту же версию без изменений, новая карточка в очередь не добавляется. Пользователь получает сообщение, что эта версия уже на проверке.
- Если SEO-специалист изменил карточку и отправил ее снова, старая активная заявка по этой сущности помечается как `superseded`, а новая версия становится активной в очереди.
- Для согласователя такая новая карточка получает маркер `Обновлено` и дифф относительно предыдущей заявки. Если предыдущей заявки нет, дифф строится относительно опубликованной версии.

Это не бизнес-оценка важности изменения. Любое отличие payload считается новой версией; полезность изменения оценивает человек.

## Журнал

Журнал - это owner-facing read model поверх `audit_events`.

- События физически не удаляются из `audit_events` в рамках этой фичи.
- Окно `30 дней` - это только правило рендера на экране проверки.
- Retention/cleanup, если понадобится, должен проектироваться отдельно как ops-политика, а не как часть UI журнала.
- В журнал не выводятся revision id, fingerprint, raw payload, технические детали БД и служебные JSON.
- Пользовательский смысл события важнее инженерного: кто, когда и что сделал с материалом.

## Что не открывать заново без отдельного решения

- Не возвращать отдельный большой блок `Как устроена очередь` на экран проверки.
- Не добавлять второй ряд статусов, если уже есть фильтры и статус на карточке.
- Не создавать отдельную таблицу журнала для тех же действий, которые уже живут в `audit_events`.
- Не показывать согласователю fingerprint, revision id, raw payload или внутренние ключи событий.
- Не превращать дифф в рекомендательную систему. Дифф только показывает изменение.
- Не смешивать `approve` и `publish`: согласование не публикует материал.

## Правила для новых эпиков

- Если фича касается воспоминания о действиях, сначала проверь `audit_events` и `lib/admin/review-journal.js`.
- Если фича касается повторной отправки, сначала проверь `computeContentFingerprint` и `submitRevisionForReview`.
- Если фича касается визуального сравнения, сначала проверь `buildHumanReadableDiff` и `ReviewContentDiffSummary`.
- Если фича касается состава очереди, сначала проверь `getReviewQueue`, `filterPendingReviewQueueItems` и `buildOwnerReviewGalleryCards`.
- Если нужен быстрый фильтр, сначала переиспользуй существующий статус или тип из `filterOwnerReviewGalleryCards`; не добавляй второй review-flow без отдельного решения.
- Новый persistent storage нужен только если появляется новый домен данных, которого нет в ревизиях или audit events.
- Owner-facing UI должен говорить простым языком: материал, действие, человек, время, что изменилось.

## Проверка после изменений

Минимальный набор для review-эпиков:

- targeted tests для измененного read model или workflow;
- `npm test`, если менялась общая логика ревизий, audit events или UI контракты;
- `npm run build` перед доставкой на сервер;
- live smoke `/admin/review` после деплоя, если задача включает сервер;
- проверка, что дерево чистое перед коммитом/после доставки, если задача включает git.
